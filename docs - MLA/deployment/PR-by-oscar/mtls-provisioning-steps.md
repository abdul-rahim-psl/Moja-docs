## The steps

To complete the trust relationship, the MLA (Paysys/Transactional Switch) side follows these steps:

1. **Generate the client key and CSR**, on the host/environment where `cch-mla` actually runs (the
   private key never leaves this side):

   ```bash
   openssl req -new -newkey rsa:2048 -nodes \
     -keyout client.key -out client.csr \
     -subj "/C=<TBD>/O=<TBD>/CN=<TBD>"
   ```

   CN, O and C values to be agreed with COMESA/DRPP before generating — sent in advance so the client
   certificate can be allow-listed on their side.

2. **Send only `client.csr`** to COMESA/DRPP (the CA owner) for signing. Never send `client.key`.

3. **Receive back**, over the same secure channel:
   - `client.crt` — the signed client certificate.
   - the COMESA/DRPP CA bundle (root and any intermediates) — needed so `cch-mla` can validate the
     server certificate presented by the Tazama ingress gateway (`mla-interconnect.paysyslabs.com`).

4. **Provision the Kubernetes secret** from the three resulting files:

   ```bash
   kubectl create secret generic cch-mla-ppa-mtls --namespace mla \
     --from-file=client.crt=client.crt \
     --from-file=client.key=client.key \
     --from-file=ca.crt=<received-ca-bundle>
   ```

5. **Configure `cch-mla`** to present `client.crt`/`client.key` and trust `ca.crt` for its connection to
   `https://mla-interconnect.paysyslabs.com` — no change to the secret's structure or mount path from
   what `deploy/kubernetes/README.md` already describes.

This is a one-time exchange, not a recurring one: MLA is reissued a new client certificate only if this
CA is ever replaced, following the same steps.
