## Finding 1 — a review can credit a PR for code the PR didn't touch

`cch-rule-002` PR #7's review praised "the historical query's settlement filter (`TxSts = 'ACCC'`)" as an improvement in that PR. Diffing `src/rule-002.ts` on `dev` against the PR branch directly shows the `TxSts = 'ACCC'` line is **unchanged, pre-existing code** — the diff only touches the message-type guard, a field-path rename, and comments. The query body itself was never edited.

**Why it matters beyond one wrong sentence:** the same read-the-final-file-in-isolation habit that produces false praise also hides a real bug in the same file — see Finding 2. Reading a diff line-by-line against the base branch, rather than reading the final state and judging whether it "looks right," is the only way to catch either failure mode.

**Template addition to make:** the "Query correctness hunt" (`Claude_PR_Review_Template.md` §2.1) currently covers parameterization, tenant scoping, and settlement correlation, but doesn't say to check whether the query was actually touched by the diff at all before attributing behavior to the PR. Add a line: confirm whether a query cited in the review was part of the diff's own changed lines, not just present in the file's final state.

## Finding 2 — a message-type rebind leaves stale literals behind, and the fix is to grep the whole function, not just re-read the guard

`cch-rule-002` PR #7 changed the binding guard from `isPacs002Transaction` to `isPacs008Transaction` (correct, matches the FSD's "POST /transfers + POST /fxTransfers" spec for rule 002) and updated the timestamp field path accordingly. But the SQL query two lines below still reads `TxTp = 'pacs.002.001.12' AND TxSts = 'ACCC'` — i.e. the rule now triggers on inbound pacs.008 transfers but still counts historical **pacs.002 settlement rows**, anchored on a pacs.008 timestamp. This is a real correctness bug (counting the wrong thing, and a systematic time-alignment error), not a style nit, and the review missed it entirely — see Finding 1's root cause.

**The critical companion fact, found while reading `cch-rule-001` PR #12 for comparison:** rule-001's own query has an `earliest_success` CTE that *also* filters `TxTp = 'pacs.002.001.12'` — and there it is **correct**, because that CTE is deliberately correlating a pacs.008 sighting back to a pacs.002 settlement confirmation, per the FSD's stated design for rule-001 (§6/001: "Estimates how long the creditor's account has existed... Add identityResolutionViaCorrelationId... so FX-leg receipts still count toward the creditor's account age via correlation"). Same literal, same surrounding shape (a message-type-mismatched string inside a query near a changed guard), opposite verdict.

**Template addition to make:** add a named hunt — "message-type rebind hunt": whenever a guard clause's bound type changes, grep the entire function body (not just the guard) for every literal and field path tied to the *old* type, and check each one individually against that specific rule's own FSD entry before deciding whether it's a leftover bug or a deliberate correlation. Do not pattern-match "this looks like the rule-002 bug" onto a different rule without checking its own FSD intent — the same code shape can be a bug in one rule and correct by design in another.

## Finding 3 — a second review round with fewer findings is not evidence the first round's findings were resolved

`cch-rule-001` PR #12's two review rounds are two days apart, same reviewer. Diffing the two reviewed commits directly (`gh api .../compare/<round-1-sha>...<round-2-sha>`) shows **only CI/workflow files and `package.json` changed between rounds** — `src/`, the tests, and `README.md` are byte-identical to round 1. Round 2's review body is much shorter than round 1's and opens with "Core pacs.008 banding logic... [is] correct," raising only one blocking item (the `accountKey` schema parameter) plus two follow-ups.

Checked individually against the current (round-2) code state, several of round 1's findings are **still unfixed and simply not restated** in round 2: the `oldest_sent` CTE still isn't settlement-correlated (ST-001 AC5), the query still only accepts `TxSts = 'ACCC'` and not `ACSC` (both required per the FSD's own §5.2 shared lookup table), and a missing `cdtrAcctId` still throws instead of returning `.err`. Only one round-1 item (`.x00` not implemented) was actually fixed between the two commits.

**Template addition to make:** §4 ("Multi-round PRs") already says each prior item gets a Resolution Status, sourced from what the user pastes in. Strengthen this: before writing a follow-up round, diff the two reviewed commits directly (`git diff <round-1-sha> <round-2-sha>` or the GitHub compare API) to establish what code actually changed, rather than inferring it from the new review's own scope. A shorter or narrower second review is not itself evidence of resolution — every prior item must be checked against the current diff individually and given an explicit Resolution Status, including items the newer review doesn't mention.

## Finding 4 — the same reviewer can give inconsistent remedies to the same unfixed fact across rounds

Both rounds of `cch-rule-001` PR #12 agree on the same underlying fact: `DataCache.cdtrAcctId`/`dbtrAcctId` is already a composite key assembled upstream (by `tms-service`), so `accountKey` as declared has nothing left to gate. But the two rounds prescribe different fixes for it:

- Round 1: **reword** the comment/README — they currently say `accountKey` is "not wired" and that DataCache has "no composite-key field," which round 1 says is factually wrong; keep the parameter, correct the prose.
- Round 2: **remove** the parameter from the schema entirely — "there's nothing left for this parameter to gate."

The code is unchanged between rounds (Finding 3), so this isn't the reviewer responding to a fix that landed differently than expected — it's the same static fact given two different prescriptions two days apart.

**Template addition to make:** when consolidating or following up on a prior round's finding, check whether the new round's remedy for the same fact matches the prior round's remedy. If it doesn't, that ambiguity should be surfaced to the PR author explicitly (e.g. "round 1 asked to reword this; this round asks to remove it — removal supersedes, following up on the stricter fix") rather than left for the author to reconcile silently.

## Finding 6 — the FSD can explicitly justify an "inert" parameter's existence, and the template's own settled-fact framing can look inconsistent until the platform-wide constraint is applied

`cch-rule-003` PR #7's review recommends removing all four of `accountKey`, `identityResolutionViaCorrelationId`, `identitySourceStage`, `transactionStage` — consistent with the template's own stated settled, fleet-wide recommendation. Checked against the FSD directly (§6/003, "Account Dormancy (CDTR)"), these four are not incidental scaffolding: the FSD explicitly lists them as required "Parameter changes" for this rule, and rule-001's FSD entry (§6/001, which rule-003 explicitly says has "the same" runnability check) states *why* — `identityResolutionViaCorrelationId` exists "so FX-leg receipts still count toward the creditor's account age via correlation back to the customer-facing transfer," and `transactionStage: transfer` exists so the signal is "based on settled transactions only, not quotes." Read in isolation, that looks like exactly the template's own category **(d)** ("genuinely blocked by a real, named external gap... a legitimate TODO, should stay declared"), not category (c) — a live tension with the review's "remove all four" recommendation.

It resolves once the template's own platform-wide constraint is applied: pacs.009 is confirmed **permanently, fleet-wide out of scope** (not blocked pending a library fix — genuinely never coming, explicitly superseding the FSD's `008+009` bindings for this rule's whole cluster). Since `identityResolutionViaCorrelationId`/`identitySourceStage` exist specifically to handle the FX-leg (pacs.009) case, and that case will never occur, the blocker isn't "unconfirmed, revisit later" (d) — it's "the case this parameter exists for cannot ever happen" (c) after all, and removal is correct. `transactionStage` resolves the same way via a different route: the review notes (correctly, checked against the code) that this rule already counts settled history unconditionally, so the parameter gates nothing regardless of pacs.009.

**Template addition to make:** when an "inert" parameter's own FSD entry states a reason for its existence that sounds like a real, unresolved blocker, don't stop at "the FSD says why it exists" — check whether that stated reason is itself something the platform-wide constraint (or another settled fact) has since voided. The template's category (c) vs (d) test should explicitly say: a parameter whose sole justification was a now-permanently-out-of-scope case (FX-leg/pacs.009) has moved from (d) to (c), even though the FSD text describing it hasn't been rewritten to say so. This is a case worth writing out in full once in the template, since encountering it fresh per-rule (as this session did) costs real time working out that the tension is apparent, not real.

This is the single highest-value gap found in this calibration pass so far — cross-PR consistency, not just within-PR correctness.

## Finding 8 — `txStsSuccessCodes` is a named, opt-in cross-cutting parameter, not a universal requirement, and this sharpens (not weakens) the "missing ACSC" finding

The FSD's §5.1 Cross-Cutting Parameter Reference defines `txStsSuccessCodes` as a real, declarable config parameter — "Explicit lookup mapping `TxInfAndSts.TxSts` values to success/fail," default `success: ACSC, ACCC; fail: RJCT, CANC` — and §5.2 gives its full lookup table (`ACSC`/`ACCC` = success, `RJCT`/`CANC` = fail, `PDNG` = neither). Checking which rules' own §6 "Parameter changes" line actually lists it: **rules 006, 010, 011, 016, 017, 020, 021, 024, 025, 026, 027, 083, 084, 090, 091 do; rules 001, 002, 003, 004 do not.** Neither rule-001's nor rule-003's code declares `txStsSuccessCodes` in its Zod schema — both simply hardcode `TxSts = 'ACCC'` inline in the SQL.

**This refines Finding 3/pattern #4, not contradicts it.** The "missing ACSC" gap on rule-001 (round 1 of PR #12, still unfixed) is not "a required config parameter was dropped" — rule-001 was never asked to take `txStsSuccessCodes` as one of its own parameters. It is a **hardcoded literal that is incomplete relative to the FSD's own §5.2 lookup table**, which the rule doesn't declare as configuration but whose values (`ACSC`+`ACCC` = settled) are still the FSD's stated definition of "settled" wherever a rule's logic needs that concept — which rule-001's/rule-003's queries plainly do (`WHERE ... TxSts = 'ACCC'` is exactly a settled-transaction filter, just an incomplete one). The category matters for how a review states the finding: not "the config schema is missing a field," but "this hardcoded settlement filter only recognizes one of the two TxSts values the FSD defines as settled."

**Rules 006, 010, 011 are next in the review queue and are exactly the rules that FSD-require `txStsSuccessCodes` as a declared parameter** — for those, the bar is different and stricter: check that the parameter is actually declared in the schema (not just that the query's hardcoded filter happens to be complete), and that it's read and applied, not just validated. This is the FSD/story-wiring hunt applied to a specific, now-confirmed-relevant parameter name, ahead of reaching those PRs.

## Finding 9 — the Dev Config Guide states explicitly, in its own words, how a pacs.008-bound rule should handle an unsettled transaction — `.x00`, not a thrown error, not a silent pass-through

`Tazama_Rules_Developer_Configuration_Guide.docx` §4.2 ("The exit policy — `.x00` and `.x01`") states directly: *".x00 means the rule stopped before banding: the transaction was not settled, or there was insufficient history to compute the metric... This is also the answer to how a rule bound to pacs.008 handles the settlement status that only arrives on pacs.002: if the transaction has not reached a terminal success status per `txStsSuccessCodes`, the rule exits with `.x00` and contributes nothing."*

This is a stronger, more direct anchor than anything cited so far for the settlement-correlation gap (Findings 3 and 7 above; pattern #2 in the library). Previously that gap was inferred from ST-001 AC5 and the asymmetric shape of the query's own two CTEs (one correlates through `pacs.002`, the other doesn't). The Dev Config Guide instead states the *required outcome* directly and unconditionally, independent of any specific rule's query implementation: an unsettled pacs.008-bound transaction must produce `.x00`. Neither rule-001 nor rule-003's current code does this — both throw `Error` on a missing `cdtrAcctId`/`dbtrAcctId` in one path, and neither's history query filters out unsettled activity on the "how long has this account been active without interruption" side of the calculation (rule-001's `oldest_sent`, rule-003's `newest_sent`) even though both correctly filter to `TxSts = 'ACCC'`-only on the settlement-correlation side (`earliest_success`/`all_success`).

**Template addition to make:** cite `Tazama_Rules_Developer_Configuration_Guide.docx` §4.2 directly (not just the FSD's ST-00x acceptance criteria) as the authority for the settled-only-history requirement — it is more specific and more binding than inferring the same conclusion from a query's own asymmetric shape. Add it as a named citation in the "Settlement-correlation gap in a dormancy/age query" pattern-library entry.

## Finding 13 — a third distinct reason a parameter can be "inert," beyond the two already established

Findings 6 and 10 established two categories for an unwired-but-FSD-justified parameter: (c) the case it exists for is now permanently out of scope (the pacs.009/FX-leg constraint), and (d) it's blocked on a genuinely unconfirmed external fact (the `transaction` table's own column schema). `cch-rule-007`'s `identitySourceStage` is neither. The FSD defines it (§5.1) as "which message in the chain is authoritative for identity" — relevant when a rule's logic branches on how identity was populated. Rule-007's actual implementation reads `Purp.Prtry` from the raw historical document store unconditionally, regardless of which stage populated it — there is no branch point in this rule's own logic left for the parameter to gate, now or ever, independent of any external blocker or platform-wide constraint. The review calls this out precisely: "genuinely inert by design... not the usual blocked/out-of-scope pattern."

**Template addition to make:** add a third category alongside (c) and (d) — call it (e): the parameter is declared per the FSD's cross-cutting definition, but this specific rule's own implementation has no decision point the parameter could ever gate, independent of any external blocker. Distinguish it explicitly from (c) (blocked by a fact now permanently voided) and (d) (blocked by a fact still open) — an (e) finding doesn't wait on anything to resolve; it should say so plainly rather than being filed under the same "blocked, TODO" framing as (d).

## Finding 14 — a mismatched fallback between a query's own bound and a later comparison's bound can invert an exit code's meaning

`cch-rule-008`'s `maxQueryLimit` has no schema default (`z.number().positive().optional()`, unchanged from `dev`, matching the FSD's "Keep maxQueryLimit" instruction — this parameter isn't new to the PR). The query only appends `LIMIT $4` `if (maxQueryLimit !== undefined)`; when it's unset, the query returns the debtor's *entire* settled-transaction history, unbounded. The post-query check `newestPacs008.length > (maxQueryLimit ?? 3)` then uses a **different**, hardcoded fallback of `3` — so a debtor with, say, 10 lifetime settled transfers and no configured `maxQueryLimit` gets `10 > 3 → true`, which the code reads as "insufficient history" and returns `.x00` for. That is backwards: more history is being read as *less* history, because the query's own bound and the comparison's bound are supposed to represent the same concept but only one of them has a working default. Traced through step by step and confirmed correct, including that the review's proposed fix (`.default(3)` on the schema) actually resolves it — it makes `LIMIT` always apply, which caps `newestPacs008.length` at the same value the comparison uses, making the `>` branch permanently false (dead but harmless) while leaving the genuine "fewer than 2 results" `.x00` condition intact.

**Also confirmed:** this exact defect is currently **inert in production** — a separate, newly-added guard (`identityResolutionRule === undefined → .err`) runs first and fires on every real invocation today, since COMESA hasn't supplied that parameter's content yet (FSD §5.1/§10 open item #1, confirmed: "identityResolutionRule... must be defined per deployment; no safe default"). The review states this precisely: "currently masked by the `identityResolutionRule` guard returning `.err` first, but it will surface as soon as that guard is lifted." This is a materially different shape from every prior "unwired parameter" finding — it isn't dead code sitting behind a permanent blocker, it's a live bug sitting behind a *temporary* one, which will start firing incorrectly the moment COMESA's answer arrives and the guard is removed. Worth its own category in the pattern library, distinct from patterns 6–10 (all of which concern parameters that stay inert, not ones whose defect is merely deferred by an unrelated guard).

**Template addition to make:** add a hunt for mismatched fallbacks — whenever a query applies an optional `LIMIT`/bound conditionally, check that every later comparison against "the configured limit" uses the *same* value (including its default, or lack of one), not an independently hardcoded fallback. ## Finding 16 — a self-referential "find myself in settled history" check silently inverts meaning under a message-type rebind, and is the most severe bug caught in this calibration pass so far

`cch-rule-010`'s `e2eIndex` check reads the current transaction's own `EndToEndId` and searches for it among rows where `TxTp = 'pacs.002.001.12' AND TxSts = 'ACCC'` (settled confirmations). Pre-PR, the rule was bound to pacs.002 — the transaction being evaluated *is* a settlement confirmation, so it trivially finds its own row (or an equivalent one) in that settled-history query; the check functioned as a real, load-bearing "do I have enough settled history to compute a baseline" gate. Post-PR, the rule is rebound to pacs.008 (correctly, matching the FSD's "POST /transfers + POST /fxTransfers" binding) — but the transaction being evaluated is now, by definition, an unsettled transfer *request*; settlement only arrives later on a separate pacs.002 message. Its own `EndToEndId` can never appear in a settled-pacs.002 query result at the moment it's being evaluated. Traced precisely: `e2eIndex` resolves to `-1` on essentially every real invocation, and `(e2eIndex < 0)` then fires `.x00` unconditionally — the rule contributes nothing on any live transaction, silently. This is a stronger, more consequential failure mode than any prior finding in this fleet: not a wrong band, not a missed success code, but the entire rule going dark in production while reporting a "successful," clean exit code every time.

**Independently confirmed the review's claim that tests mask this rather than catch it**: `__tests__/unit/rule.test.ts` line 152 explicitly sets `req.transaction.FIToFICstmrCdtTrf.CdtTrfTxInf.PmtId.EndToEndId = 'test-id'` to match a mocked query-result row — manually forcing the exact condition (this transaction's own `EndToEndId` already present in *settled* history) that real data can structurally never produce for an unsettled request being evaluated in real time. A green test suite here proves nothing about the real defect; it proves the mock was constructed to avoid triggering it.

**Template addition to make:** add this as its own named hunt, generalized beyond this one rule — "self-reference hunt": whenever a rule's query searches for the *current* transaction's own identifier inside a result set filtered to a *different*, more-advanced state (e.g. searching for the current pacs.008's `EndToEndId` among settled pacs.002 rows), check explicitly whether that self-lookup can ever succeed given the current transaction's own guaranteed state at the point of evaluation. This is the same underlying hazard as the "stale message-type literal" hunt (pattern #3), but inverted and easy to miss precisely because the *literal* (`'pacs.002.001.12'`) is correct and deliberate here — it's the self-referential comparison built around it that silently breaks.

## Standing pattern library (carried forward, checked against every new PR)

Confirmed blocker-shaped defects seen so far in this fleet — check each new PR's diff against all of these explicitly, regardless of whether the PR's own review mentions them:

1. **CI/workflow org-reversion — check direction, not just presence of an org-name change.** A PR that changes `.github/workflows/*.yml` *from* `psl-izyane-cch-frms/workflows` *to* `frmscoe/workflows` (i.e. away from what `dev`'s current file uses) is the blocker; the reverse direction (fixing a file that still incorrectly says `frmscoe/workflows` on `dev`) is a legitimate correction, not a finding. Always diff against `dev`'s current file to establish which direction is correct before flagging. Seen: `cch-rule-001` PR #12 round 1 (caught, wrong direction, blocker); `cch-rule-003` PR #7 (wrong direction, missed); `cch-rule-010` PR #7 (right direction on `publish.yml`, correctly not a finding — Finding 18).
2. **Settlement-correlation gap in a dormancy/age query** — a CTE that counts raw `pacs.008` sightings by account identity with no join back to a successful (`TxSts` success-code) `pacs.002`, while a sibling CTE in the same query *does* do that correlation. Real accuracy gap, directly required by `Tazama_Rules_Developer_Configuration_Guide.docx` §4.2 ("if the transaction has not reached a terminal success status per `txStsSuccessCodes`, the rule exits with `.x00`") — not inferred, stated. Seen: `cch-rule-001` PR #12 round 1 (caught, blocker); `cch-rule-003` PR #7 (self-disclosed by author, missed by reviewer).
3. **Stale message-type literal inside a query after a guard-clause rebind** — grep the whole function body, not just the guard, for the old type's literals; check each one individually against that rule's own FSD entry, since the same shape can be a bug (rule-002) or deliberate correlation (rule-001/003's `earliest_success`/`all_success` CTEs). Seen: `cch-rule-002` PR #7 (missed, approved anyway).
4. **Missing success code in a `TxSts` filter** — the FSD's §5.2 shared lookup defines `ACSC`+`ACCC` as settled/success. A rule whose own §6 entry declares `txStsSuccessCodes` as a parameter must wire it (schema + read + correct value) — a missing/unread declaration there is a wiring gap. A rule whose §6 entry does *not* list `txStsSuccessCodes` (001, 002, 003, 004) but hardcodes `TxSts = 'ACCC'` inline is a different, narrower finding: an incomplete literal relative to §5.2's definition of "settled," not a missing config field — state it that way, don't conflate the two (Finding 8). Seen: `cch-rule-001` PR #12 round 1 (caught, blocker; not fixed by round 2, not re-raised).
5. **`.err` vs. thrown `Error` on an unresolvable identity** — ST-00x.X-style specs generally want `.err`, not an uncaught throw, when e.g. `DataCache.cdtrAcctId`/`dbtrAcctId` is missing. Seen: `cch-rule-001` PR #12 round 1 (caught, blocker); `cch-rule-003` PR #7 (missed); `cch-rule-006` PR #7 (missed); `cch-rule-007` PR #7 (missed); `cch-rule-008` PR #7 (missed) — **missed on four consecutive PRs after being established as a blocker; treat as near-certain on every remaining PR in the queue** (Findings 11-12, 15).

Checked on `cch-rule-006` PR #7: declared correctly, but unread — a real, correctly-flagged wiring gap (Finding 10), distinct from an undeclared parameter. 7. **An "unread" config parameter is not automatically removable** — when several parameters in the same rule are all unwired, check each one's own blocker individually rather than applying one verdict to all. `accountKey`'s blocker (composite identity, upstream-owned) resolves via the platform-wide pacs.009 constraint (category c, removable); a blocker resting on an unconfirmed `transaction`-table column schema (`amountBasis`, `restrictToSameCurrency`, `txStsSuccessCodes` on rule-006) is a separate, still-open fact the platform-wide constraint doesn't touch (category d, stays declared). Seen: `cch-rule-006` PR #7 (correctly split four parameters into remove-one/keep-three; Finding 10).
8. **A self-referential counting function's band boundaries must be checked against what the function actually counts, not just against the Dev Config Guide's literal numbers.** When a function always includes its own reference value in a count (e.g. comparing `amounts[0]` against itself), the minimum possible count is 1, not 0 — band boundaries taken verbatim from a spec that assumes a 0-based, non-self-inclusive count will misclassify the "nothing matched" case. Check any "count of similar/matching X" function for whether it includes the reference item, and cross-check band boundaries against that specific behavior, not just against the spec's stated numbers in isolation. Seen: `cch-rule-006` PR #7 (caught correctly, blocker).
9. **A band-count reduction stated in the FSD/README but not carried through to the config schema/tests** — when a rule's FSD entry says "reduce from N bands to M," check the actual band count in `ruleConfig.ts`'s default/schema and in every test fixture, not just the README's own stated band table. A rule can correctly narrow its *output logic* (e.g. only ever emitting two possible values) while its *declared config* still carries the old band count with an unreachable middle band — the code comment may even say so explicitly without the config being fixed to match. Seen: `cch-rule-007` PR #7 (caught correctly, blocker; Finding 12/"What got right").
10. **A parameter can be inert for a third reason beyond "blocked by a voided FSD justification" (c) or "blocked by an open external fact" (d): the rule's own logic has no branch point the parameter could ever gate, independent of any blocker** — call this (e). Don't file an (e) finding under the same "blocked, TODO, revisit later" framing as (d); it isn't waiting on anything. Seen: `cch-rule-007` PR #7's `identitySourceStage` (Finding 13).
11. **A mismatched fallback between a query's own conditional `LIMIT` and a later comparison's hardcoded fallback can invert what an exit code means** — check that every place a "configured limit" value is used shares the exact same default (or absence of one), not independently duplicated fallbacks. A bug of this shape can be currently unreachable/masked by an unrelated early-exit guard (e.g. a different mandatory parameter failing validation first) — note explicitly that it's a real, live bug that will surface the moment that guard is lifted, not dismiss it as currently-dead code. Seen: `cch-rule-008` PR #7 (caught correctly, blocker; Finding 14).
12. **Verify commit author/committer mismatches with `gh api repos/<org>/<repo>/commits/<sha>` (returns `commit.author.name` and `commit.committer.name` separately), not `gh pr view --json commits`** (only surfaces one identity per commit, via `authors`). 13. **A self-referential "find my own identifier in a more-advanced-state result set" check silently inverts under a message-type rebind.** When a rule's own identifier is searched for inside a query filtered to a later pipeline state (e.g. searching the current pacs.008's `EndToEndId` among *settled* pacs.002 rows), check explicitly whether that self-lookup can structurally ever succeed given the current transaction's guaranteed state at evaluation time — a check that was trivially true pre-rebind (the current transaction already *was* that later state) can become trivially false post-rebind (the current transaction is evaluated *before* reaching that state). The most severe defect shape found in this fleet so far: it doesn't misclassify an outcome, it silently disables the rule entirely while reporting a clean exit. Seen: `cch-rule-010` PR #7 (caught correctly, blocker; Finding 16); `cch-rule-011` PR #7 (caught correctly, blocker, confirmed byte-for-byte identical — its FSD-designated mirror; Finding 19).
14. **A commit message claiming to "restore," "revert," or "align" a file to match a reference branch is a claim, not a verification** — diff the named file's actual current content against that reference directly rather than trusting the message. Seen: `cch-rule-010` PR #7's `package-rule-rc.yml` (Finding 17) — a "replaced changed workflows with dev versions" commit that did not, in fact, match `dev`'s `rule_number` value; `cch-rule-011` PR #7 (Finding 20) — **two** such commits in its history, error still present at the actual head, and present in *both* `package-rule.yml` and `package-rule-rc.yml`.
15. **A defect found via a copy-paste-shaped branch name (identical `feat/xxx` name reused across sibling repos) should be checked directly on every other PR sharing that branch name, not treated as a one-off.** `feat/iaa` (rule-010, rule-011) both carried the identical `rule_number: "001"` copy-paste error; `feat/ots` (rule-006, rule-007, rule-008) is worth the same direct check if any CI-config identity field is ever suspected on one of them. Seen: `cch-rule-010`/`cch-rule-011` PR #7s (Finding 20).
16. **No identity-presence guard at all (not even a throw) before an unresolved `DataCache` field flows into a query parameter** — distinct from pattern #5 (`.err` vs. thrown `Error`, which at least fails in some form). Confirmed pre-existing and unchanged by their respective PRs on both `cch-rule-010` (`dbtrAcctId`) and `cch-rule-011` (`cdtrAcctId`) — not a new PR issue, but a fleet-wide gap worth its own entry for any future work touching these two rules specifically (Finding 21).

## Standing calibration rules for the review pass ahead

Carried forward into every PR review from here on, independent of whether `Claude_PR_Review_Template.md` is itself amended to state them:

1. Diff the base-branch version of every touched function against the PR-branch version directly — never judge correctness from the final file state alone.
2. On any message-type rebind, grep the whole function body for literals/field paths tied to the old type, and check each one against that specific rule's own FSD entry — don't pattern-match a verdict from a different rule's PR.
3. Before writing a follow-up round on a PR we're tracking, diff the two commits being compared to establish what code actually changed, and give every prior finding an explicit Resolution Status — including ones a newer round doesn't mention.
4. If our own follow-up would prescribe a different remedy than a prior round did for the same fact, say so explicitly rather than silently superseding it.
5. Mark claims resting on repos/systems outside this workspace as unverifiable-from-here, distinct from claims checked directly against the FSD/Dev Config Guide/local diff.
6. Check every new PR's diff against the standing pattern library above, mechanically, regardless of what that PR's own posted review does or doesn't mention — a defect confirmed as a blocker once elsewhere in the fleet does not get rediscovered from scratch each time, and its absence from a later review is not evidence it isn't present.
7. When a config parameter looks FSD-justified but also matches the fleet-wide inert-parameter pattern, check whether the FSD's own stated reason for it rests on something the platform-wide pacs.009 constraint (or another settled fact) has since voided, before treating the FSD text as still live justification.
8. When several parameters in one rule are all unwired, check each one's own blocker individually — don't assume a uniform verdict (remove all / keep all) just because a sibling rule's PR had one.
9. For any "count of similar/matching X" function, check whether it counts the reference item against itself before trusting a Dev Config Guide band boundary taken at face value — a self-inclusive count needs boundaries shifted by one relative to what the spec's literal numbers assume.
10. When the FSD/README states a band-count reduction, check the actual band count in the config schema/tests directly — a narrowed output range and a narrowed declared band list are two different things, and only checking the code's output logic can miss a still-present, now-unreachable band left in configuration.
11. When a parameter is inert, identify which of three distinct reasons applies before writing the finding: (c) its justification is voided by a settled fact like the pacs.009 constraint, (d) it's blocked on a genuinely open external fact, or (e) this rule's own logic has no branch point for it to ever gate, independent of any blocker. State which one plainly — don't default to "blocked, TODO" framing for an (e) case.
12. When a query applies a bound (e.g. `LIMIT`) conditionally on a parameter being set, check every later use of "that same limit" for a matching default — a mismatched fallback between the query and a post-query comparison can invert what an exit/outcome means, and can hide behind an unrelated early-exit guard until that guard is lifted.
13. Check commit author/committer mismatches via `gh api repos/<org>/<repo>/commits/<sha>`, not `gh pr view --json commits` — the two identity fields can differ on the same commit, and the weaker check can silently pass where the review's own claim is actually correct.
14. When a rule's guard clause changes bound message type, check every self-referential lookup (the current transaction searching for its own identifier in a history query) for whether it can structurally still succeed given the current transaction's guaranteed state at evaluation time — not just whether the query's literals are individually correct.
15. Treat any PR-diff CI/workflow change as requiring an explicit direction check against `dev`'s current file before judging it a regression or a fix — an org-name or workflow-target change is only a finding in the direction that moves away from `dev`'s current, correct value.
16. When a commit message claims to have restored/reverted/aligned a file to a reference branch, verify by diffing that file's actual content against the reference directly — don't accept the message as the check.
17. When checking a claim scoped to "a commit" within a PR (identity mismatch, a specific change), read the full commit list and identify which commit it actually concerns — a claim about an earlier commit is not verifiable by inspecting the head commit alone.
18. When a review states a defect is "the same as" one found on a sibling PR, re-verify it directly on the new PR's own code rather than accepting the analogy — the FSD's own "mirror of rule X" framing is a strong prior, not a substitute for checking.
19. When a copy-paste-shaped identity branch name (`feat/xxx` reused verbatim across sibling repos) is seen, check any defect found on one repo sharing that branch name against every other repo sharing it.
