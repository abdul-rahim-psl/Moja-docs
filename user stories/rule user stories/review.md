## 3. Critical findings

### C1 — An unweighted outcome silently zeroes the whole typology; it does not stall

**The backlog states**, in §0.1 and in substantially every EP-4 and EP-5 story:

> "If a rule returns an outcome the typology configuration does not weight, that typology never completes. The evaluation hangs."

**What actually happens.** Completion and scoring are separate mechanisms.

*Completion* is a headcount — `typology-processor/src/logic.service.ts`:

```ts
if (networkMapRules && typologyResultRules.length < networkMapRules.rules.length) continue;
```

The rule executer **always** emits a result, including on both error paths, so the count is always reached. Weights play no part in completion.

*Scoring* is where it fails — `typology-processor/src/utils/evaluateTExpression.ts`:

```ts
ruleResults.forEach((r) => {
  const values = valueMap.get(`${r.id}${r.cfg}${r.subRuleRef}`);
  if (values) { ruleTermMap.set(term, wght); r.wght = wght; }   // no else branch
});
const expr = replaceTerms(typologyExpression, ruleTermMap);      // unmatched termId left as a string
const returnValue = computeEngine.box(expr).evaluate();
if (typeof returnValue.value !== 'number' || returnValue.errors.length > 0) {
  loggerService.error(`Expression evaluated to non numeric number: …`);
  return 0;                                                      // whole typology → 0
}
```

An unweighted `subRuleRef` leaves its `termId` unbound in the MathJSON expression. Evaluation yields a non-numeric result and the guard returns **0 for the entire typology** — discarding every other member rule's evidence with it. The typology result is still constructed, still stamped `review: false`, and still forwarded to TADProc.

**Why this matters more, not less.** A stall is loud: a missing typology result is conspicuous. A silent zero is invisible — the typology reports normally and simply never alerts. The remedy (weight every emittable outcome; enforce it in `US-702`) is exactly right and becomes *more* important. Three things need correcting:

- **US-704 AC-4** asks for "a stall-detection test [proving] that an unweighted outcome causes the typology to fail to complete." That test cannot pass as written. It should assert the typology **completes with a score of 0** and that the error is logged.
- **US-706** monitors `.err` rates, but nothing watches for `Expression evaluated to non numeric number`. That log line is the only runtime symptom of the defect class this backlog is built around.
- **US-003 AC-7** has a developer "deliberately cause it once and observe the typology fail to complete." They will observe a zero score instead, and may reasonably conclude the configuration is fine.

A secondary diagnostic is available: `r.wght` is only stamped when a weight matches, so an unweighted outcome leaves the rule result's `wght` unset in the alert payload.

**Amendment.** Restate the mechanism in §0.1 and the EP-5 preamble; keep every completeness AC unchanged; re-scope US-704 AC-4; add log-based detection to US-706 and to US-606's pre-activation checks.

### C2 — The trigger message is `pacs.002`, not `pacs.008`

**The backlog states** a binding of `pacs.008.001.10` (+ `pacs.009.001.07`) on 30 of 31 rule stories; GA-3 states "Only `pacs.008.001.10` is ingestible by stock Tazama 4.0.0 today"; US-603 makes the `pacs.008` branch "the only branch fully testable under GA-3, and therefore the branch that proves the whole routing model"; US-126 describes rule 076 as "**the only rule bound to `pacs.002`**".

**What the platform does.**

> "The default configuration of the system only evaluates the **pacs.002 as the trigger payload** for the rule processors and typologies."
> — `docs/Product/configuration-management.md` §1

- The seed network map has exactly **one** `messages[]` branch: `txTp: "pacs.002.001.12"`, `id: "004@4.0.0"`. All 31 typologies and all 33 rules plus EFRuP hang off it. There is no `pacs.008` branch and no `pacs.009` branch.
- **26 of the 30** in-scope rules present in `rule-collection` open with a hard type guard returning `.err` for anything that is not a `pacs.002`.
- Rule 001 is representative: triggered by a `pacs.002`, it then queries `pacs.008.001.10` and `pacs.002.001.12` rows to derive creditor account age. `pacs.008` is *history*, not trigger.
- `pacs.002.001.12` is as ingestible as `pacs.008.001.10`. GA-3 is true as far as it goes but omits the message that actually matters.

Rule 076 — the one rule the backlog binds to `pacs.002` — is the one case where its binding matches the platform, and it treats that as the exception rather than the rule.

**Impact.** If EP-6 is built as specified, every rule routed on the `pacs.008` branch returns `.err`, every `.err` is weighted 0 (correctly, per GA-6 and the seed), every typology scores 0, and nothing alerts — while US-603 AC-5's "no typology hangs" **passes**, because `.err` is a weighted outcome and the typology completes cleanly.

The consequences reach beyond EP-6:

- The `pacs.008` / `pacs.009` split underpins US-705's FX-coverage measurement and US-810's position on FX under-scoring. Both rest on a binding table that does not describe the platform.
- The "ten `pacs.008`-only rules" (006, 007, 008, 018, 021, 024, 025, 026, 027, 078) and every per-message maximum and threshold in EP-5 derive from that table.
- US-601's route analysis is arithmetically sound but computed over routes that do not exist in this form.
- US-006's forecast of "approximately 57 typology configuration documents" collapses toward 30 if the platform model is adopted.

**Amendment.** A scope decision, to be taken before any EP-5 or EP-6 story is estimated:

1. **Adopt the platform model** — route on `pacs.002.001.12`, treat `pacs.008`/`pain.001` as history, rewrite the binding tables. Cheapest; matches the seed; makes the whole rule set testable today.
2. **Fund the trigger change** — modify each rule's type guard and DataCache expectations to accept a `pacs.008` trigger. This is 26+ processor changes, well beyond `.2` sub-task sizing, and it redefines "history" for every rule.

Either way, restate GA-3 as: *four message types are supported — pain.001.001.11, pain.013.001.09, pacs.008.001.10, pacs.002.001.12; `pacs.009` is unsupported anywhere in the platform; the default trigger is `pacs.002.001.12`.*

### H2 — Day-based target bands would silently disable rules 001, 003 and 004

Rule 001 returns `timeDifferenceInMs`. The seed bands are in milliseconds — 86 400 000 / 2 592 000 000 / 7 776 000 000, exactly 1 / 30 / 90 days. The US-101 target is:

| Outcome | Lower | Upper | Severity |
|---|---|---|---|
| `.01` | 0 | 1 | 1.0 |
| `.04` | 90 | +∞ | 0.0 |

Loaded as written against an unmodified processor, every metric above 90 ms — that is, every transaction — lands in `.04` "Established account", severity 0.0. The rule contributes nothing, forever, without erroring. Rules 003 and 004 have the same shape (90 / 365 days against millisecond metrics; the seed's 7 889 229 000 / 31 556 926 000 are exactly 3 and 12 months).

**The seed already expresses the target's intended structure, in milliseconds.** For 001 the seed's four bands are the target's four bands. For 003 and 004 the seed's three bands are the target's three bands, at 3 and 12 months against the target's 90 and 365 days. The change is a unit conversion and nothing else.

The backlog flags the risk in prose for 001 ("Convert or the `.02` band means 1–30 *milliseconds*") and handles rule 076 exemplary well. But the target tables are stated only in days, and no story requires the processor to change its return unit.

Two platform details belong in the same amendment, both affecting US-033's generator:

- **`lowerLimit: 0` does not bound a band.** The check is `(!band.lowerLimit || value >= band.lowerLimit)` — a falsy test. The target tables use `lowerLimit: 0` on rules 001, 003, 004, 006, 008, 021, 044 and 045; the seed omits the bound instead. Harmless today, but it hides intent.
- **Band array order decides ties** — `determineOutcome` breaks on first match. A generator must emit bands in ascending order.

**Amendment.** Express all time-based target bands in milliseconds, the platform convention. Add a US-703 check that every time-derived boundary is ms-scaled, and US-033 acceptance criteria for ascending order and for omitting rather than zeroing an open lower bound.

### H3 — Unbounded target bands would stop rules 002, 016 and 017 ever firing

The target tables for rules 002, 016, 017 and 007 specify **no boundary on either band**:

| Rule | Target `.01` | Target `.02` | Feeds |
|---|---|---|---|
| 002 | −∞ → +∞, severity 0.0 | −∞ → +∞, severity 1.0 | 11 typologies |
| 016 | −∞ → +∞, severity 0.0 | −∞ → +∞, severity 1.0 | **17 typologies** |
| 017 | −∞ → +∞, severity 0.0 | −∞ → +∞, severity 1.0 | 13 typologies |
| 007 | −∞ → +∞ | −∞ → +∞ | 2 typologies (also a cased conversion) |

Against `determineOutcome`, a band with neither limit matches every value and `break`s the loop. **`.01` — the zero-severity "no convergence detected" band — would swallow every transaction, and `.02` would be unreachable.** Rules 002, 016 and 017 would return a severity-0.0 outcome on every transaction, forever, silently.

Rules 016 and 002 have the widest fan-out in the set (17 and 11 typologies). Rule 017 feeds 13. Between them they are members of most of the register.

The backlog does gate this — US-102 says "Confirm the intended convergence threshold before authoring — an unstated boundary cannot be configured" — which is the right instinct. What is missing is the consequence: the failure is not a load error but a permanently zero-scoring rule. The seed supplies the answer directly: **5** for rules 002 and 016 (24h window), **5** for rule 017 (8h window), and the backlog already states those correctly in its "current" tables.

**Amendment.** Populate the target boundaries from the seed before authoring, and add a US-703 / US-702 check that no band in any configuration omits both limits.

### H4 — EP-2's schema premise is inverted

**The backlog states** (EP-2 preamble): "Each rule validates its configuration against a Zod schema declaring exactly the keys it accepts… A parameter the schema does not declare never reaches the rule." US-010: "without it, no COMESA rule configuration will load."

**What the schema does** — `frms-coe-lib/src/schemas/ruleConfig.ts`:

```ts
parameters: z.record(z.union([z.string(), z.number()]), z.unknown()).optional()
```

An **open record with `z.unknown()` values**. Any key of any type — including objects such as `corridorThreshold` — validates today. No rule schema in `rule-collection` uses `.strict()`, so unknown keys are never rejected anywhere.

The second half of the sentence is right and is the whole problem: `handleTransaction` reads only the keys it was coded for. A new parameter loads cleanly and is **inert**.

**Impact.** US-010 is not a gate on loading COMESA configurations. It should be re-framed as defensive validation — which is what its acceptance criteria already describe. AC-2 (reject invalid enum values), AC-4 (reject parameters a rule does not consume) and AC-5 (named startup error for mandatory parameters) all require *adding* strictness that does not exist, and are worth doing: a typo in a parameter name currently disables a control silently. The real gate on EP-4 is the per-rule `.2` code work.

**Amendment.** Restate US-010's rationale; keep its acceptance criteria; remove it from the critical path as a blocker and re-sequence it as parallel hardening.

### H6 — EFRuP is the genuine stall risk, and it is handled only implicitly

Because completion is a headcount, a rule listed in the network map that never delivers a result **does** stall the typology — this is the real stall mechanism, and the backlog does not name it.

Exactly **eight** seed typologies list `EFRuP@4.0.0` as a member rule: **028, 037, 044, 045, 047, 095, 179, 185**. GA-6 correctly omits `flowProcessor` from the workflow block, and that is schema-valid. But the backlog never states that **EFRuP must also be removed from `rules[]` in every network-map branch**. Carrying the seed's membership forward while not deploying the event-flow processor would stall those eight typologies indefinitely.

US-602's structural validator (AC-7) checks for typologies with zero rules and for non-member rules — it does not check for EFRuP.

**Amendment.** Add an explicit acceptance criterion to US-602 and US-606 asserting EFRuP's absence from every branch; add the same assertion to US-702. Note in §0.1 that a missing rule result — not an unweighted outcome — is what stalls a typology.

### H7 — COMESA's scoring model is a substantial recalibration of the seed, and this is nowhere recorded

Three independent changes compound, and none is flagged as a departure:

**(a) Role assignments differ from the seed's tiering in 28 of 30 typologies.**

The seed encodes a three-tier model in its weights — top-band weights of 400 / 200 / 100. Comparing the implied tier against the backlog's `primary` / `supporting` / `contextual` role, only 2 of 30 typologies agree. The disagreement is systematic and directional:

| Rules | Seed tier | Backlog role |
|---|---|---|
| 024, 025, 026, 027, 090 (mirroring, upstream divergence) | **top** (400) | supporting |
| 010, 011, 020, 048 (volume / amount vs history) | **top** (400) | supporting |
| 002, 016, 017 (convergence / divergence) | mid (200) | **primary** |
| 083, 084 (multiple accounts) | low (100) | **primary** in typologies 003, 013, 105, 107 |

Typology 001 is representative: all 12 members disagree. The backlog promotes the convergence rules to primary and demotes the mirroring rules to supporting — the inverse of the seed's emphasis.

**(b) Alert thresholds are doubled in relative terms.** The seed's working convention is 17–33% of reachable maximum (median ≈ 24%). The backlog mandates 50% (US-033 AC-4), with 137 and 191 at 100%.

**(c) Band boundaries are made markedly more sensitive.** Notably:

| Rule | Seed bands | Target bands | Effect |
|---|---|---|---|
| 010, 011, 020, 048 | <3 / 3–5 / 5+ | <1 / 1–2 / 2+ | z-score trigger moves from ~3σ to ~1σ |
| 024, 025, 026, 027 | <2 / 2+ | <1 / 1+ | mirroring fires on a single match |
| 044, 045 | <1 / 1–2 / 2–3 / 3+ | 0–5 / 5–20 / 20+ | scale change plus band drop |
| 090 | <3 / 3+ | <5 / 5–15 / 15+ | less sensitive |
| 021 | <4 / 4+ | 0–2 / 2–5 / 5+ | more sensitive |

None of these is wrong. Role assignment is a detection-design choice, the backlog derives roles from the COMESA register rather than from Tazama, and GA-7 correctly holds every value provisional. But (b) pushes alert volume **down** while (c) pushes it sharply **up**, and (a) redistributes evidence across the register — so the net effect on alert rates is genuinely unpredictable, and GA-7's "an alert rate observed in FUT is not a defect until tuning has run" could mask any of the three.

**Amendment.** Record (a), (b) and (c) explicitly as deliberate departures from the seed, with the seed's tiering, percentage and boundaries carried into US-706's pre-tuning baseline as the comparison point. US-706 AC-5 already annotates four typologies expected to behave unusually; this belongs alongside it.

### H8 — Identity de-duplication must happen before tokenization, or it becomes impossible

`identityResolutionRule` (US-015, US-802) is the backlog's one 🔴 *blocker for promotion*. The ingestion design that has to supply it does not, and the order in which two not-yet-built components run decides whether it can ever be supplied.

**What the ingestion design defines.** [MLA-PPA-Technical-Design.md](poc-mla-ppa/docs/MLA-PPA-Technical-Design.md) keys everything on the payment, never on the party:

| §3.4 purpose | Key |
|---|---|
| Transaction state, all stages | `transactionId` / `transferId` |
| Quote stage | `quoteId` |
| FX quote stage | `conversionRequestId` |
| FX transfer stage | `commitRequestId` |
| Notification dedup (§3.2 step 4) | `transferId` alone |

"Dedup" in that document always means *message* dedup. There is no party key, no `PartyIdType` handling and no alias-resolution rule anywhere in it. The only identity-adjacent content is §2.1's PII component, which "deterministically tokenizes party-identity fields" — which fields is never stated, and §5.3 lists it as **not started**.

**What the key actually is.** Tazama's TMS builds both identity keys by string concatenation, identically on `pacs.008`, `pain.001` and `pain.013` (`tms-service/src/logic.service.ts`):

```ts
dbtrId     = Dbtr.Id.PrvtId.Othr[0].Id + Dbtr.Id.PrvtId.Othr[0].SchmeNm.Prtry
dbtrAcctId = DbtrAcct.Id.Othr[0].Id + .SchmeNm.Prtry + DbtrAgt.FinInstnId.ClrSysMmbId.MmbId
```

So the effective keys today are **person = `<partyId><partyIdType>`** and **account = `<partyId><partyIdType><fspId>`**.

**The over-count is arithmetic, not a data-quality risk.** Because `SchmeNm.Prtry` sits *inside* both keys, one customer transacting under MSISDN, ALIAS and DEVICE identifiers produces three distinct `dbtrId` values and three distinct `dbtrAcctId` values. Rules 083 and 084 count distinct accounts, so they will count three. US-015's premise is confirmed by construction, and US-802's warning that typologies 003, 013 and 105 over-fire is not a possibility but a certainty.

**The ordering constraint.** Deterministic tokenization **preserves the over-count and makes it unfixable downstream.** Token(MSISDN) and Token(ALIAS) remain two different values — per-field tokenization does not merge aliases — and once tokenized, the raw identifier can no longer be resolved against any lookup to find the underlying wallet. The de-duplication must therefore run **before or inside** the tokenizer, which must tokenize a *resolved canonical party id* rather than each raw identifier.

Neither document states this, and it is cheap now and expensive later: the tokenizer has not been built (§5.3), so the ordering is still a free choice.

**There is also no source for the resolution in the current pipeline.** The Account Lookup Service would know, but Open Item #4 records that ALS is HTTPS end-to-end and never publishes to Kafka, so the PPA cannot observe it. The canonical id must therefore come from a new DFSP/ALS lookup or a COMESA-supplied mapping.

**Amendment.** Sharpen US-802 from "supply the de-duplication logic" to three concrete questions, and raise the first two against the ingestion workstream rather than the rule workstream:

1. What resolves an MSISDN / ALIAS / DEVICE identifier to a single canonical wallet id, and can the PPA call it?
2. Will the PII component tokenize that canonical id rather than each raw identifier — i.e. does de-duplication run before tokenization?
3. If neither is available, is the interim FUT position (accept the over-count, measure it, hold 003/013/105) still acceptable given the over-count is guaranteed rather than probable?

Add the ordering constraint as an explicit dependency on US-015, and record it against the ingestion design so it is decided before the tokenizer is built.

## 8. Closing assessment

The backlog's central instinct — that outcome completeness is the defect class that will hurt this deployment, and that it must be enforced by machine rather than by review — is correct, and it is Tazama's own stated doctrine (*"Every. Possible. Outcome."*). The seed proves the discipline is achievable: 31 typologies, 1 473 weights, zero gaps. `US-702` deserves the priority the backlog gives it and slightly more, because the failure it prevents is silent.

Where the backlog reasons from the platform's own artefacts it is consistently right — the typology register, the exit-condition inventory, the `.x03` argument, the rule 078 remap and the two seed defects it catches are all confirmed. Where it goes wrong, it goes wrong by working from a stale picture of the deployed configuration rather than from the shipped seed: the trigger message, the band counts, and the unbounded convergence boundaries all sit in that category, and all three are resolved by reading `tms-configuration-main/curl/` — which GA-10 and the `.1` sub-tasks already instruct the team to do.

The two structural corrections are the trigger-message model and the failure-mode description. Both are knowable from the platform in a day, and both are far cheaper to fix now than after 31 rule configurations and 57 typology documents have been authored against them.
